> Goal: a service prints a hash and waits for the password that produced it. Get it right and it prints another one. Three stages, and it never says which algorithm made any of them.

## Approach

Connect and the pattern is immediately clear: a bare hex string, a prompt, and nothing else to work with. A correct password advances to the next stage and the next hash.

```bash frame="code" title="Bash"
┌──(Idan@Kali)-[~/hashcrack]
└─> nc verbal-sleep.picoctf.net <port number>
```

The algorithm is the thing being withheld. Each stage names it only in the line it prints *after* a correct answer, which is too late to be of any use, so the only clue available in advance is the width of the digest: 32 hex characters, then 40, then 64, which is 128, 160 and 256 bits.

Width narrows the field without settling it. A 128 bit digest is equally consistent with MD4, MD2, NTLM and RIPEMD-128; 160 bits fits RIPEMD-160 as well as SHA-1; 256 bits fits SHA3-256 and BLAKE2s-256. What makes the guess safe here is context rather than arithmetic: in a beginner challenge the common member of each set is the intended one, and a wrong guess costs nothing because the crack simply fails and you try the next candidate.

In the event the identification never had to happen at all. CrackStation takes a bare hash with no algorithm selector, searching every table it holds and reporting whichever one matched, so all three stages came back on a paste.

## Why it works

None of these algorithms is broken, and nothing here is cryptanalysis. Both properties that matter are properties of the deployment: the digests are unsalted, so a single precomputed table serves every target that ever used them, and the three passwords were already sitting in that table. The guess about which algorithm made each one is checkable after the fact and holds, since `md5` of `password123`, `sha1` of `letmein` and `sha256` of `qwerty098` reproduce the three digests exactly.

Stage three is the interesting one. SHA-256 is not weak and it is genuinely more expensive per candidate than MD5, yet it falls just as easily, because cost per guess only begins to matter once the answer is not already in the list. That is why the remedy is a per-password salt, which makes one table useless against a second target, and a deliberately slow function such as bcrypt, scrypt or Argon2, which makes the list expensive to walk. A stronger hash on its own buys nothing, which is what the flag says out loud.
